V5 用于 iOS、macOS、Android 和 Windows。三份客户端工程共享 Rust OpenMLS、SAS 及恢复文件实现，各自负责凭据存储、快照验证和媒体门控。下文的 Keychain、ContinuousClock、RTP 提供器和音频生命周期细节以 Apple 实现为例。[V5 开发文档](e2ee-v5-development.md) · [共享 MLS](../Client/apple/MLS/native/src/lib.rs) · [Apple 媒体适配](../Client/apple/Shared/LiveKitCallMedia.swift) · [Android 手册](../Client/android/README.md) · [Windows 手册](../Client/windows/doc/README.md) · [附件格式](attachments.md)

## 身份、凭据和信任根

Passkey 向业务服务证明账号登录，原生 Bearer 证明当前登录，入房授权证明当前房间资格，LiveKit JWT 允许建立媒体连接。客户端独立身份、设备证书及持钥证明绑定实际 MLS 参与者，SAS 与账号共享的个人信任决定是否达到全员互认；未经核验时只交换控制消息，不开放内容。这些材料各有职责，登录 credential、JWT 和入房密码都不是媒体密钥。

| 材料 | 保存位置与期限／退役 |
| --- | --- |
| Passkey 私钥 | 设备／密码管理器；服务端保存公钥凭据，删除账号不能远程删除设备记录 |
| WebAuthn challenge | SQLite 中的一次性短期记录，浏览器仪式最长 5 分钟 |
| 浏览器会话 | 随机 Cookie，服务端存摘要，最长 8 小时；HttpOnly、SameSite=Strict，HTTPS 下 Secure；角色变化／停用／退出会撤销 |
| 原生授权码 | 服务端存摘要，绑定签发客户端和 S256 PKCE，最长 1 分钟。兑换要求该客户端对应的平台及固定回调，只能成功一次。 |
| 手机授权 | 最长 3 分钟，绑定客户端并校验私有 verifier。发起端从已批准请求领取短期设置授权，最终设备验证成功才发业务 credential |
| 身份设置授权 | 最长 5 分钟，绑定服务 origin、账号、客户端、S256 PKCE 与候选公钥挑战；不能入房、读取共享状态或替换在线登录 |
| 客户端 credential | 服务端存 SHA-256 摘要，有效期取登录后 20 小时与设备叶证书到期时间的较早者。新登录替换旧登录。各客户端仅在进程内存中保存登录凭据 |
| 入房 proof | 服务端进程随机 HMAC-SHA256 签名，最长 30 秒，绑定登录／房间／序列／密码版本；进程重启后未使用 proof 失效 |
| 准确入房记录 | SQLite，绑定 login、room、entry。有效心跳可续期，每次签发或续期后最多有效 30 秒，且受当前登录截止时间约束 |
| LiveKit JWT | app 与 LiveKit 共用 API secret 签发和校验令牌，默认有效 5 分钟。可发布麦克风轨道、订阅轨道和发布数据。公开 Compose 从共享卷的 `keys.json` 读取部署专用 secret |
| 账号 Ed25519 根私钥 | 首次获批登录时本机随机生成；仅初始化／恢复的临时内存中使用，不明文落盘、不入 Keychain、不上传、不复制到剪贴板 |
| `.chirpkey` | 用户导出的加密账号根备份，由原文件密码在本机解锁。见[离线身份恢复文件规范](chirpkey.md) |
| 设备 Ed25519 私钥、证书与账号本机材料 | 按规范 origin 与不可变账号 ID 隔离，退出登录或会话被接管时保留。Apple 使用 Data Protection Keychain（AfterFirstUnlockThisDeviceOnly，关闭同步） |
| 好友与个人信任 | 本人设备签名的连续账号事件链及删除记录。授权服务保存事件正文，向经验证的本人设备提供完整视图，向其他读者仅提供社交正文摘要。客户端验证历史前缀 |
| 授权快照签名 seed | 公开镜像内置与客户端配套的公开 seed，用于签署授权快照。私有部署可挂载自用 seed 并替换客户端公钥 |
| Android APK 签名私钥 | 开源版密钥库和构建口令随源码分发。任何持有源码的人均可用同一证书签名，证书指纹只能辨认签名密钥。独立发行者可使用自己的签名身份。[Android 签名说明](../Client/android/signing/README.md) |
| 授权撤销 | 主服务授权日志永久记录；客户端每 20 秒刷新完整挑战快照，从请求开始最多有效 60 秒，本地保存最高头与撤销墓碑 |
| 业务黑名单 | 只能缩减准入权限；不能授予信任，不能替代签名授权快照 |
| MLS Ed25519 身份私钥 | 客户端原生上下文内存，绑定准确入房；每轮使用新 KeyPackage 和新群组 |
| MLS 群组秘密与发送者材料 | 客户端内存；例行轮换可短时保留当前与候选状态，切换后退役旧材料；成员变化／暂停／离房清理，不持久化 |
| 附件密钥 | 每文件独立随机 256 位密钥，仅当前入房可撤销 lease 内存；离房或清缓存退役 |

## 设备身份、恢复与 SAS 互认

签名与 MLS 传输仍使用 `chirp-mls-authenticated-v5` 的规范字节域；生产房间采用确定的公开 mutual context，不再从房主白名单取得成员资格。Swift 与原生 Rust 分别验证设备证书、设备签名的准确入房绑定、MLS 公钥、完整名单、配钥包和全员确认签名，不能只信服务端的 `ready` 或“已信任”字段。旧房主策略 HTTP 路由已移除。

账号获批并通过 Passkey 验证后，四个平台均先取得五分钟设置授权。首次设置时，客户端生成候选根、设备与密码加密的恢复文件，完成导出和用户确认，再签署绑定候选设备的一次性挑战。服务端在同一写事务重查资格、验证证书与持钥证明、首次绑定根、登记设备并替换登录。并发首绑只有一个根获胜。响应丢失后重新认证并复用原候选，存储损坏或根冲突时须显式处理。[设置授权与最终激活](../internal/store/identity_setup.go)

文件和密码同时泄露会暴露账号根私钥。对另一个副本重新加密后，泄露的副本仍可由原密码解锁。文件格式、秘密生命周期及失败行为见[离线身份恢复文件规范](chirpkey.md)。

新设备二维码授权使用 `chirp-device-pair-v1`。二维码只包含新设备签名的公开请求：规范 origin、不可变账号 ID、预期账号根、候选设备公钥、随机 nonce、有效期及预先固定的 SAS 承诺。旧设备从本机已保存身份核对根与账号，双方用独立的原生 vodozemac 上下文计算完整三组数字并确认不同角色的 MAC。新设备也必须人工确认旧设备屏幕上的安全码，不能仅接受服务端“已批准”。每条中转消息签名覆盖请求摘要、操作、准确签发设备摘要和完整 payload；首次 offer 固定后不得替换。旧设备仅在双方 MAC 验证及本机系统身份认证成功后签发候选公钥的证书，服务端不接触身份私钥。实现见[签名协议](../internal/identity/device_pairing.go)、[短期中转](../internal/store/device_pairing.go)与[客户端配对状态机](../Client/apple/Shared/DevicePairingSession.swift)。

摄像头扫描和图片导入使用同一配对协议，图像在本机识别。Android 从系统图库选择图片，Windows 按文件内容读取系统支持的单帧图片，两端均使用 ZXing 识别二维码。Apple 使用 Vision 读取单帧 PNG。三个客户端导入的图片均须能识别出唯一的配对码，大小上限为 8 MiB，每边最多 4096 像素。[Apple 图片读取](../Client/apple/Shared/DevicePairingImages.swift) · [Android 图片读取](../Client/android/app/src/main/kotlin/cn/youzifeile/chirp/ui/PairingViews.kt) · [Windows 图片读取](../Client/windows/Chirp/PairingImages.cs)

二维码携带签名请求，三组 SAS 安全码由双方设备另行计算。导入图片时，用户须在旧设备上输入新设备当前屏幕显示的全部三组数字。旧设备在输入前隐藏自己计算的数字，三次不一致即终止配对。双方应直接核对各自的原生界面。

配对请求最多五分钟，另受新设备本次 Passkey 设置授权截止约束；客户端同时使用单调时钟截止。中转复用有独立摘要命名空间及 purpose 的临时仪式存储，全局 512 项、每账号最多三项活动配对，每步重查账号、根与签发设备资格。请求与各阶段不可覆盖；丢响应后重试原消息幂等，包括审批已经推进后重试较早消息。批准只保存签名证书，不签发业务登录；新设备验签、保存候选证书、完成持钥证明后，沿用最终激活事务登记设备并替换旧会话。被踢或退出业务登录的旧设备仍可通过设备签名参与配对，撤销的设备不能继续签发。临时状态到期不会清除已保存在新设备的有效候选证书，最终激活失败可重新 Passkey 登录后继续。

此流程提高设备加入时对恶意中转的抵抗能力，依赖用户正确核对真实设备及原生客户端／操作系统可信；授权接口由主服务提供；恶意服务器可以长期隐瞒客户端尚未知晓的撤销；服务端仍可拒绝服务，用户不能用未核验语音代替独立认证渠道。

证书最多 8 层、最多五年，链和签发权限仍需验证。已登记设备独立撤销，只检查命中设备本身的撤销状态；登记新后代时重新检查签发设备当前资格。已撤销设备不能再登记新设备，但它在撤销前合法登记的后代继续有效。恢复文件可为有效账号登记全新设备，不能复活原撤销设备或被封禁账号。

[SAS 原生状态机](../Client/apple/MLS/native/src/security.rs)使用 [vodozemac](https://docs.rs/vodozemac/0.11.2/vodozemac/sas/) 的 X25519／HKDF／MAC 与完整默认三组数字显示，加入承诺、房间／本次 entry／双方账号根与设备钥绑定、用户接受、双方人工确认及不同角色的身份 MAC。事务到期、协议乱序、重放、承诺或 MAC 不匹配即终止；只有双方确认及密钥确认完成才签名保存本人对该具体设备的信任。单向添加好友不构成信任，好友删除和单设备撤销个人信任均同步本人账号，不改变对方全局资格。

房间 trusted 状态依据本人设备信任及每位参与设备签名的互认声明，声明绑定精确入会绑定（包括 entry、MLS 公钥与设备身份）。未核验成员加入时暂停整个房间，不能获得 MLS Welcome、语音、文字或附件。只有本机批准名单、授权新鲜度与全员密钥确认都通过才开放内容。设备变化必须重新核验，好友名称不能代替密码学身份。成员昵称仅作显示标签，未核验设备保留昵称并单独标明核验状态，账号和设备指纹在身份操作中显示。

请当面或通过另一条已认证渠道核对完整三组 SAS 数字。主服务在 `/authorization/v5/*` 验证登记、撤销和社交事件的当时权限，并签发绑定随机挑战的历史快照。客户端用构建时固定的公钥验签，再验证设备签名和已见历史前缀。从请求开始计算的 60 秒期限只有在取得有效新快照后才能更新。[授权协议](e2ee-v5-development.md)

业务黑名单提供额外的拒绝依据。Apple 接受有效快照后尝试更新黑名单，拉取失败保留本机记录。Windows 对已失效的业务登录返回错误，普通拉取失败沿用已知记录。Android 在验证快照并成功校验黑名单后更新授权截止。已见的黑名单、撤销或历史检查点不能被缺项或更早的响应覆盖。[Apple](../Client/apple/Shared/SocialIdentity.swift) · [Windows](../Client/windows/engine/authority_windows.go) · [Android](../Client/android/app/src/main/kotlin/cn/youzifeile/chirp/data/AccountIdentity.kt)

主服务持有授权签名密钥和授权库。仓库默认 seed 是公开材料，持有者可为旧历史签发新挑战响应。即使使用自有私钥，恶意主服务仍可长期隐瞒客户端尚未知晓的撤销。若攻击者还持有旧可信设备私钥，尚未知晓撤销的成员可能继续接纳该设备。设备签名、已验证的历史前缀和 MLS 内容密钥仍由客户端独立验证或生成。[授权密钥指南](authorization-keys.md) · [部署指南](../deploy/README.md)

## 群组配钥与媒体门控

每房独立维护群组。入房代 group ID 为 `room_id/server_id/session_id/generation`；身份为 `member_id.login_id.entry_id`。加入、离开、移除、重连及权威故障恢复均重建入房代。稳定成员的例行轮换使用独立 `key_epoch`，新的 MLS group ID 为入房代 ID 后接 `/key/{key_epoch}`；初始轮使用入房代 ID。当前使用标准 MLS KeyPackage、Add、Welcome，不实现 RFC ReInit Proposal 或长期群组的增量 Commit 同步。

1. 客户端生成临时 Ed25519 MLS 身份，提交设备签名的入房绑定；每轮生成新的、有效期 120 秒的 KeyPackage 及绑定本轮完整名单的签名。
2. 协调状态依次进入 `collecting`、`welcoming`、`confirming`、`ready`。发起者通过 OpenMLS 批量加入成员并发布加密 Welcome。
3. 每个客户端验证套件、group ID、完整成员集合、各身份签名公钥与自身绑定，并取得相同的 epoch authenticator 确认值。
4. 使用 MLS exporter 标签 `Chirp LiveKit sender key v5`，以完整发送者身份为 context，导出各自不同的 32 字节材料；秘密以固定二进制越过 C 边界，MLS JSON 传公开协议材料；恢复文件的本地安全操作会短暂传递本机密码与根种子，不发送到网络或记录日志。
5. 客户端先安装对应群组状态及媒体密钥提供器，再显式确认，包括发起者；单人和多人使用同一条媒体连接与配钥流程。所有成员确认后，准确 generation / revision / confirmation 才可取得媒体许可；建立媒体连接本身不授权采集或发送麦克风音频。

套件固定为 `MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519`。MLS 套件的 AES-128-GCM 与媒体提供器导出的 32 字节材料是不同层次，不应据此把所有链路笼统写成同一密钥或算法。

群组客户端对实际发送的 JSON 字节签名。`action` 和 `events` 都使用 POST，正文包含 `room_id`、`entry_id` 及 `operation`，事件订阅的操作是 `watch`。除 Bearer 外，还须带 `X-Chirp-Time`（Unix 秒）、`X-Chirp-Nonce`、`X-Chirp-Key` 和 `X-Chirp-Signature`。签名域 `Chirp group request v5` 绑定准确身份、方法、对应的规范房间路径、时间、nonce 和正文 SHA-256。服务端核验签名、入房资格和已绑定公钥，按成员及房间限制请求预算。[请求校验](../internal/group/action.go)

默认每 2 秒心跳，6 秒未心跳移除，转换超时 12 秒，默认每 60 秒轮转。互认房间等待人工身份核验时保持仅控制消息的成员会话，不因尚未提交 KeyPackage 而触发转换超时；全员提交包后开始计时，Welcome 发布和密钥确认仍有超时保护。等待期间仍检查心跳、身份及入房授权，不发放媒体许可。心跳只证明在线，不授予媒体许可；就绪后约每秒请求一次最长 3 秒许可。许可截止从请求发出的 `ContinuousClock` 时刻计算，网络耗时和系统休眠消耗有效期，迟到响应不重新计时。

有效登录下的许可到期会立即暂停发送、退役原媒体密钥并请求新一轮配钥，保留原入房与通话会话；恢复失败或登录／入房失效才结束通话。群组更新的客户端超时只计本轮初始化，就绪后清除，不用通话已持续的时间替代故障原因。

[媒体会话清理](../internal/httpapi/sessions.go)持续核验准确入房并移除无权连接，不能把一次移出或 JWT 截止当成完整撤销。缓存媒体令牌与数据库入房授权分别管理，成员删除、重新登录及重新入房后也按准确身份核对。

服务端默认每 60 秒触发例行轮换；客户端在本地密钥年龄 90 秒时主动重建，120 秒硬上限不受服务端配置影响。配置通过可选 `smooth_rotation` 能力在 V5 客户端间协商例行轮换；仅全部成员在签名 join 中声明支持时启用，否则使用暂停重建。V5 不回退到旧身份协议。Android 通过设备授权和房间互认后参与 V5 登录与配钥。

服务端在轮转点前 `min(12 秒, 轮转间隔/2)` 开始候选轮，保留当前轮的授权 revision 和发送许可，使用独立 `rotation_revision` 通知准备进度。客户端沿用入房身份签名密钥，在隔离的原生存储中生成候选 KeyPackage／新群组，验证完全相同的成员身份与公钥，预装所有发送者密钥后才确认。到轮转点且全部确认后，服务端进入 switching；客户端通过有序 RTC 操作切换发送槽，再报告 activation。租约绑定该成员实际激活的 key_epoch，迟到的旧 epoch 租约回复不覆盖新状态。

所有 activation 确认后完成轮转，入房代和聊天 audience 不变。客户端观察到完成后，再保留旧接收槽 1 秒处理在途帧，然后用随机材料覆盖旧槽。准备／切换最晚到轮转点后一个许可周期（默认 3 秒）；此前的租约也截短到这个截止点。超时则撤销当前与候选轮，执行暂停重建，不能无限延长旧钥。任何成员变更或权威恢复均作废候选轮；不能将已分发给原名单的候选钥用于新名单。

完整快照与心跳／许可响应附带可选 `room_information` 展示元数据：服务端采样时间、当前入房代首次就绪时间、最近一次全员激活完成时间、下次计划轮转时间、实际轮转间隔、全局密钥轮次、成员总数、候选轮阶段及确认／激活数量。时间使用 Unix 毫秒；首次就绪不算例行换钥，只有最后一位成员激活后才更新完成时间。成员变化或重建清除旧代的时间，暂停时不公布有效计划；字段不包含成员标识、地址或密码学材料，只经现有入房验证和签名接口提供，不增加公开目录接口。

这些字段是服务端提供的展示信息，不是独立的密码学时间证明，也不授予许可。Apple 客户端仅接受与已校验快照的名单数量、代次和轮换阶段一致的元数据；倒计时从服务端采样时间与计划时间的差值计算，并从请求发出的连续时钟扣除网络耗时和休眠。六秒未更新或连接暂停时标记待同步；倒计时归零不表示换钥完成。原生密钥年龄、媒体许可和全员身份核验继续独立执行，不能由展示时间续期。

激活请求在途时，客户端继续续期服务端已确认的密钥代次；收到成功确认后才推进续租代次，并取消阻塞中的旧代租约请求、立即获取新代许可。轮换期间被截短的许可提前续期，确认后的迟到旧代响应不能覆盖新状态。上述过程独立于麦克风是否开启。

媒体与数据发送的共同门控包括当前登录有效、正确 entry、媒体已连接、当前连接代次与安装密钥匹配及群组事件连接存在；麦克风发布另要求用户保留开麦意图，静音不阻止文字和附件。[本地意图 SDK 补丁](../Client/apple/Patches/livekit-local-microphone-intent.patch)拒绝信令中的远程取消静音，服务端不能绕过应用门控开启用户已静音的麦克风。失联、许可到期、撤销或群组变化时停发；恢复须新一轮密钥，不能重新安装已经退役的材料。3 秒是正常客户端的许可上限，不是任意修改客户端或整个网络撤销总时延保证。

## 媒体、文字及旧钥退役

LiveKit 使用每参与者提供器，非共享房间钥模式，键槽数为 2、自动棘轮窗口为 0，并禁用 SIF 明文绕过。例行轮换交替使用两个槽，不由旧钥推导未来钥；预装不改变当前发送索引，切换不替换 RTP 加密器、不重置帧计数器、不停麦或重启播放。新建的本地加密器继承当前发送槽。安全暂停／入房代变化仍替换整个提供器并退役所有槽。媒体发送器绑定真实 RTP 对象，缺失或替换时拒绝应用层就绪，避免重置计数器后复用旧钥。

退役提供器逐身份／槽位用独立安全随机材料覆盖并永久标记退役，即使第三方仍持有原生对象，也不能继续使用旧 MLS 材料。不能通过关闭帧加密器完成退役，因为原生 disabled 状态可能具有透传语义。Rust 清理群组及内存存储中的序列化秘密；这不构成系统分配器、在途帧和第三方内存副本的取证级擦除保证。

文字和附件描述仅通过加密专用数据发送路径发布，绑定原提供器、群组代、接收者和短期发送许可。等待可靠数据通道后再次校验，失败不转明文。接收检查 GCM、发送者、当前 group ID、序列及正文限制，拒绝错误代和重放；服务端无聊天历史。用户看到的发送成功只是本地提交结果。实现见[RoomChat](../Client/apple/Shared/RoomChat.swift)与[加密聊天补丁](../Client/apple/Patches/livekit-ephemeral-chat.patch)。

SDK 排队及可靠重发保留原发送授权，在实际提交给数据通道前重新检查期限、任务取消和提供器退役状态。已交给 WebRTC 或已到达对端的在途数据不能追回，这与禁止尚未出队的旧消息发送是不同边界。MLS 的 Swift/C 身份入口拒绝内嵌 NUL，避免两端对身份字节产生不同解释。

例行切换会撤销旧的数据发送 gate，已排队的旧发送不会静默迁移到新槽；未完成的本地发送按原失败路径保留。聊天序列与 audience 仍绑定稳定入房代，成员集合未变化时允许有限旧槽窗口内的在途密文。附件正文使用每文件独立密钥，例行轮换不更改已授权的文件接收名单。

## 房间密码与传输

房间密码只作入房验证。服务端保存 16 字节随机盐及 Argon2id verifier（2 次、19 MiB、并行度 1、32 字节输出），计算在写锁外并限制并发；正式入房在写事务内重查密码版本。改密不回收既有成员的解密能力，需要移出／结束通话等授权操作。实现见[密码验证](../internal/store/room_password.go)。

HTTPS/WSS 使用系统证书校验。业务 API、发现、群组、原生兑换及扫码 HTTP 使用拒绝重定向的会话。WSS 还经过各平台的媒体 SDK。内置 Nginx 终止 TLS 后通过同机 Docker 网络以 HTTP 访问 app 与 LiveKit，DNS 验证凭据和证书私钥位于它独占的状态目录。沿用已有 Nginx 时，证书私钥由原代理保管，跨主机上游应使用经过验证的 TLS 或加密隧道。[公开 Compose](../compose.yaml) · [已有 Nginx 的接入步骤](../deploy/README.md#使用已有-nginx-和证书)

媒体全部通过自有 LiveKit SFU 的 UDP 7882 转发，不建立客户端 P2P。服务端禁用媒体 TCP 回退、外部公网 IP 探测及 TURN；客户端 SDK 补丁在提前连接、JOIN、RECONNECT 时忽略全部外部 ICE server 列表。客户端与自有 SFU 的 ICE/STUN 连接检查仍保留；不能只凭 LiveKit YAML 判断没有访问第三方 STUN。

## 能力与验证限制

V5 客户端不向服务端交付媒体、文字或附件的解密秘密；服务器仍能观察成员、房间、IP、连接时间、大小及流量模式。当前方案不隐藏这些元数据，不提供逐帧前向保密，不撤回已经播放、截图、复制或导出的内容，也不保证被攻陷终端的安全。

仓库测试覆盖签名向量、首次绑定竞争、恢复文件互操作、SAS 与互认、设备撤销、快照前缀、名单与密钥代次、重放、RTP 绑定及提供器退役。Android 的设备联调可覆盖真实 Go 接口和本机 SFU，Windows 的引擎回归可覆盖实际 Rust DLL、双客户端媒体和附件。跨物理设备的声音、锁屏、切网、蓝牙、生产 TLS／UDP 和撤销总时延需在目标环境验收。[开发与验证](development.md) · [Android 测试](../Client/android/docs/testing.md) · [Windows 验证](../Client/windows/doc/README.md)
